# File Feature

The file feature lets Mai send and receive chat attachments: files posted in groups, files you upload in the web UI, and text Mai generates herself can all be stored and read on demand. It runs inside the main program and does not depend on the WebUI, the sandbox computer, or an external Agent.

**What it does**: store and download attachments received after an adapter connects, read common text files, and send files from the web chat. **What it does not do**: browse existing group file directories; binary formats such as Office and PDF can be stored and transferred but their content is not parsed.

## Enabling

The feature is off by default. Turn it on under WebUI "Capabilities → File Feature", or edit the config:

::: code-group

```toml [bot_config.toml ~vscode-icons:file-type-toml~]
[capabilities]
files = true    # Master switch: attachment registration, model file tools, plugin file interface, WebUI files page
```

:::

The switch hot-reloads and controls all four entry points at once. When off, new file operations are refused; **existing originals are not deleted**, and the cache cleanup policy keeps running. The WebUI switch and the HTTP service are independent — disabling the WebUI does not affect file transfers over QQ.

## Three Entry Points

**QQ** — the unified QQ connector's NapCat and SnowLuma profiles hand file messages and group upload notifications to the main program as structured attachments. The adapter's own notification switches and chat filters still apply; receiving group upload notifications requires the matching notification setting.

**WebUI** — the paperclip in the chat input uploads the attachment first, then sends it with the message. The "Files" page filters by the chat's real name and offers upload, download, text reading, and management. Removing an attachment from a draft does not delete the original; delete originals manually from the file management page.

**Model tools** — Mai can call `files_list`, `files_download`, `files_read_text`, `files_create_text`, and `files_send`, but only inside a trusted execution context: plugins cannot pick a chat by submitting a `session_id`, and scheduled tasks and plain API calls have no chat authorization either. File content is external data and is never executed as instructions.

An administrator may send across chats after picking a target chat and confirming on the file management page; ordinary tools and the plugin SDK provide no cross-chat authorization.

## Storage and Quotas

::: code-group

```toml [bot_config.toml ~vscode-icons:file-type-toml~]
[files]
max_file_mib = 50              # Per-file cap
max_storage_gib = 10           # Instance quota, covering downloads, originals, and upload reserves
max_text_mib = 8               # Text parsing cap; larger files can still be sent and downloaded
cache_days = 30                # Days to keep platform download caches
max_concurrent_transfers = 4   # Simultaneous transfer limit
transfer_timeout = 120         # Per-transfer timeout in seconds
transfer_base_url = ""         # Backend address the client can reach; empty = [http]
trusted_download_origins = []  # Intranet adapter origins allowed for downloads
```

:::

Platform attachments are registered as metadata first; content is only fetched when you explicitly ask to download or read it. Caches are cleaned 30 days after their last access. Local uploads and generated content count as originals and are kept until deleted manually. Reaching a quota refuses new additions — nothing is deleted automatically.

Transfers reserve space based on the per-file cap, so a transfer is refused even when the remaining space cannot hold one full-size file. After the concurrency cap is lowered, in-flight reads are allowed to finish while new operations follow the new limit.

Files live in the instance's `data/files` directory; disk names are generated by the main program and unrelated to upload names, and a SHA-256 is computed on first write. Text parsing supports UTF-8, UTF-16 with BOM, and explicitly specified GB18030; scripts or macros in documents are never executed.

## Same-Host and Cross-Host Deployment

File bytes travel over the shared backend at `/api/files/transfers/...`; the HTTP service starts with the main program. `webui.enabled = false` only turns off the management pages and management API — QQ and plugin transfers keep working.

When `transfer_base_url` is empty, the address comes from `host` / `port` in `[http]` (loopback and 8001 by default); `7999` is the front-end development port only. When the QQ client runs on another machine, you must fill in an address the client can reach and set up backend listening, reverse proxy, and network access; prefer HTTPS across machines.

The listen settings belong to `[http]` — restart after changing the address or port. The `HTTP_HOST` environment variable appends listen addresses. When the backend only serves file transfers, the reverse proxy can forward just `/api/files/`.

Platform downloads allow HTTP(S) only, reject credentials embedded in URLs, and check the destination of the actual DNS connection and every redirect hop; private, loopback, reserved, and multicast ranges are refused by default. If a platform hands out a private download URL, the administrator must list the exact origin such as `http://192.168.1.20:3000` in `trusted_download_origins`; wildcards are not accepted, and never list a service users control.

A token authorizes one operation on one file, expires after five minutes by default, and is invalidated entirely by a restart. Do not treat transfer URLs as permanent file links or write them into public logs; for long-term references use `file_ref`, which the backend re-authorizes per chat every time.

## Verification and Troubleshooting

**Verify** — with the switch on, upload a text file through the paperclip in the web chat; it should appear on the "Files" page, filtered by chat, and Mai should list it when asked for the current chat's files.

**Page says the file feature is disabled** — the master switch is `[capabilities].files`, not in `[files]`; save and confirm the log shows a successful reload.

**Send fails or download never starts** — platform caches download only on request; click download or read first. Check that `transfer_base_url` is an address the client can reach and that the reverse proxy forwards `/api/files/`.

**Private download address refused** — when the platform serves from a private network, put the exact `http(s)://host:port` into `trusted_download_origins`; wildcards are not accepted.

**Out of space although space seems free** — transfers reserve the per-file cap up front, so starting is refused when the remainder cannot hold one full-size file; lower `max_file_mib` or clean up originals and retry.

**File cannot be deleted** — cleanup and deletion are refused while a transfer token is valid or a download response is in progress, to keep the bytes being read stable; retry after the transfer ends.
