# File Capabilities

File capabilities let MaiBot receive and send chat attachments, keep files, and read common text files. They run inside the main program and do not depend on the WebUI or an external agent; `webui.enabled = false` only closes the management pages and does not affect sending or receiving.

Files arriving as chat attachments, local uploads, and generated text are supported. Existing group file directories are not traversed. Office, PDF, and other binary files can be stored and transferred but their contents are not parsed.

## Enabling

Turn it on in **WebUI → Capabilities → File capabilities**, or set `capabilities.files = true` in `bot_config.toml`. The switch hot-reloads and controls attachment registration, model tools, the plugin SDK, and the file HTTP entry point together.

When it is off, new file operations are rejected, existing originals are kept, and cache cleanup policies keep running. The HTTP server and the WebUI switch remain independent.

## What each entry point does

::: fields
- **QQ** — The OneBot Adapter delivers received file messages and group upload notices to the host as structured attachments. Receiving group upload notices requires the matching notification setting.
- **WebUI** — The paperclip in the chat composer uploads an attachment before sending the message. The **Files** page filters by real chat name and supports upload, download, text reading, and management. Removing a draft attachment does not delete the original; delete it from file management instead.
- **Model** — `files_list`, `files_download`, `files_read_text`, `files_create_text`, and `files_send` only accept the current trusted execution context. File contents are external data and never execute as tool instructions.
- **Administrator** — Cross-chat sending requires selecting the target chat on the Files page and confirming. Regular tools and the plugin SDK expose no cross-chat authorization.
:::

## Storage and quotas

The `files` section is generated by the config system — no manual directories or database edits:

::: code-group

```toml [bot_config.toml ~vscode-icons:file-type-toml~]
[files]
max_file_mib = 50                 # Per-file limit (MiB), checked against actual received bytes
max_storage_gib = 10              # Instance quota (GiB), including downloads, originals, and in-flight reservations
max_text_mib = 8                  # Text parsing limit (MiB), up to 50; larger files still transfer and download
cache_days = 30                   # Days to keep platform download caches after last access; local originals never auto-delete
max_concurrent_transfers = 4      # Concurrent uploads and downloads, 1-32
transfer_timeout = 120            # Per-transfer timeout in seconds, 10-3600
trusted_download_origins = []     # Internal adapter sources allowed for download, exact http(s)://host:port
```

:::

Platform attachments register metadata first; content is fetched only when a download or read is explicitly requested, and caches are cleaned `cache_days` after last access. Local uploads and generated content are originals and stay until deleted by hand. Reaching the quota rejects new files instead of deleting originals. Transfers reserve the per-file maximum up front, so a transfer is refused when the remaining space cannot fit one more maximum-size file.

Files live in the instance's `data/files`; the host generates on-disk names unrelated to the uploaded filename and computes SHA-256 on first write. Text reads page by characters, up to 32000 per read, and support UTF-8, UTF-16 with BOM, and explicitly specified GB18030. Document scripts and macros are never executed.

## Same-machine and cross-machine setups

File bytes travel over the host's unified address, `/api/files/bots/<bot_id>/transfers/<token>`. The host listens on port 8001 of `127.0.0.1` and `::1` by default, and every bot shares that one outward address; 7999 is only the frontend dev server port.

The address lives in the `[webui]` section of the host config `host/config.toml`: `hosts` and `port` decide what it listens on, `public_base_url` decides the outward address used to build file links, and changing either needs a host restart. If the QQ client runs on another machine, set `public_base_url` to an address the client can reach, open the listener, and configure a reverse proxy; prefer HTTPS across machines. The `HTTP_HOST` environment variable appends a listen address, which is how Docker exposes the container NIC.

When only file transfer is exposed, the reverse proxy can forward `/api/files/` alone.

## Download allowlist

Platform downloads allow HTTP(S) only and reject credentials embedded in URLs. The actual DNS connection and every redirect hop are checked against loopback, private, reserved, and multicast ranges, which are blocked by default.

If a platform hands out a private-network download URL, list the exact origin in `files.trusted_download_origins`, for example `http://192.168.1.20:3000`. Wildcards and user-supplied download addresses are not allowed.

## Tokens and references

A token authorizes one operation on one file, expires after five minutes by default, and all tokens die when the service restarts. Never treat a transfer URL as a permanent link or write it into public logs.

For long-lived references use `file_ref`; the backend rechecks chat authorization on every access. While a send credential is valid or a download response is in flight, cleanup and deletion are refused so the bytes being read stay fixed.

## Plugin integration

The SDK 2.17.0 `ctx.files` is available during tool calls dispatched by the host. Declare the exact `files.*` capability names in the plugin manifest; the host issues chat permission when the call starts and revokes it when the call ends or is cancelled — the SDK cannot choose a chat by passing a `session_id`. Scheduled tasks, plain API calls, and calls without a chat context are refused.

The plugin reads upload paths locally and streams over HTTP; downloads exclusively create a local target file and verify size and hash. The host rejects arbitrary local paths, arbitrary download URLs, and large Base64 blobs sent over RPC. During development, point `MAIBOT_PLUGIN_SDK_PATH` at a local SDK checkout.

Sending returns `sent` or `unknown`. `unknown` means no definitive success receipt was obtained and the platform may still deliver later — check the chat and do not resend automatically.

## Verify and troubleshoot

**Verify** — In the WebUI chat composer, attach a text file with the paperclip and send it with a message. Filter the **Files** page by that chat: the file should be listed, downloadable, and readable online.

- **No paperclip** — Confirm **Capabilities → File capabilities** is on and `capabilities.files` is `true`.
- **Upload refused** — Check the file against `max_file_mib` and the instance against `max_storage_gib`; hitting the quota never deletes old files.
- **Remote QQ client receives no files** — Check that `webui.public_base_url` in `host/config.toml` points somewhere the client can reach, that `webui.hosts` listens externally, and that the reverse proxy forwards `/api/files/`.
- **Private-network download rejected** — Add the exact origin to `files.trusted_download_origins`; wildcards will not work.
- **Link expired** — Transfer tokens expire after five minutes by default; use `file_ref` for long-lived references.
